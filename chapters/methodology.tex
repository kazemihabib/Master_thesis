\chapter{Methodology and Experimental Framework}
\label{chap:methodology}

This chapter presents the methodology and experimental framework designed to benchmark and evaluate Multimodal Large Language Models (MLLMs) for zero-shot and few-shot face-swap detection. Rather than fine-tuning models on task-specific datasets, this work evaluates the intrinsic visual forensic capabilities of off-the-shelf instruction-tuned MLLMs under controlled prompting regimes.

The remainder of this chapter is organised as follows:
\Cref{sec:formulation} defines the formal task formulation and deterministic response-parsing protocol;
\Cref{sec:datasets} details the benchmark datasets, manipulation generators, and the balanced development set;
\Cref{sec:compute_env} describes the compute environment on which all experiments were run;
\Cref{sec:engine} motivates the choice of inference engine and batching strategy;
\Cref{sec:models} presents the evaluated model suite;
\Cref{sec:metric} defines the evaluation metric and the configuration-selection protocol shared by the search phases;
\Cref{sec:pipeline} details the experiment pipeline and its GPU memory-isolation architecture;
\Cref{sec:staged_prompting} details the staged zero-shot prompt engineering funnel; and
\Cref{sec:few_shot_method} describes the few-shot in-context learning experimental design.

% -------------------------------------------------------------
\section{Problem Formulation and Response Parsing}
\label{sec:formulation}

\subsection{Mathematical Task Formulation}

We formulate single-image face-swap detection as a binary classification problem. Let $\mathcal{X}$ denote the space of RGB facial images. An input image $x \in \mathcal{X}$ is associated with a ground-truth label $y \in \mathcal{Y} = \{\text{real}, \text{fake}\}$, where:
\begin{itemize}
    \item $\text{real}$ ($y = 0$): corresponds to an authentic, unaltered facial photograph of a person;
    \item $\text{fake}$ ($y = 1$): corresponds to a digitally manipulated image in which the facial identity of the original subject has been replaced by a target identity via an automated face-swapping algorithm.
\end{itemize}

Let $m$ denote an off-the-shelf instruction-tuned MLLM. Given an input facial query image $x$, a prompt $p$, and a hyperparameter configuration $\theta_{\text{gen}}$ (such as sampling temperature and maximum output sequence length), the model autoregressively generates an output text sequence $t$:
\begin{equation}
    t = m(p, x; \theta_{\text{gen}})
\end{equation}

\subsection{Prompt Parameterization}

In typical applications, prompts are formulated as monolithic text strings. However, modifying multiple prompt aspects simultaneously makes it impossible to isolate which specific factor drives changes in model performance. To enable controlled and systematic evaluation, we formulate a prompt $p$ as a modular tuple of five distinct components:
\begin{equation}
    p = \langle \mathcal{V}, \mathcal{S}, \mathcal{R}, \mathcal{C}, \mathcal{D} \rangle
\end{equation}
where:
\begin{itemize}
    \item $\mathcal{V} = (w_{\text{real}}, w_{\text{fake}})$ specifies the \textbf{target class vocabulary} words the model is instructed to output for real and fake faces (e.g., \texttt{("authentic", "faceswapped")});
    \item $\mathcal{S}$ defines the \textbf{extra context} provided in the system or user prompt;
    \item $\mathcal{R}$ specifies the \textbf{persona} in the systemp prompt (e.g., \emph{Forensic Video Analyst} );
    \item $\mathcal{C}$ governs the \textbf{reasoning mode} determining whether and how the model should produce a reasoning for it's choice (e.g. Chain-of-Thought);
    \item $\mathcal{D} = \{(x_1^{(d)}, y_1^{(d)}), \dots, (x_n^{(d)}, y_n^{(d)})\}$ denotes the \textbf{in-context demonstration set} of $n$ labelled visual exemplars ($n = 0$ in zero-shot configurations).
\end{itemize}

This decomposition directly enables the staged experimental funnel described in \Cref{sec:staged_prompting} and the few-shot protocol in \Cref{sec:few_shot_method}.

\subsection{Deterministic Parsing and Failure Semantics}

Because MLLMs emit natural language, benchmarking their predictions requires a deterministic mapping from the generated token sequence $t$ to the binary label space $\mathcal{Y} = \{\text{real}, \text{fake}\}$. We define a deterministic parser $\pi(t)$ that maps the generated output to a predicted label according to the declared extraction policy:
\begin{equation}
    \hat{y} = \pi(t) \in \{\text{real}, \text{fake}, \bot\}
\end{equation}
where $\bot$ denotes a distinguished \textbf{parse-failure} symbol emitted when the model fails to produce an output that can be mapped to either \emph{real} or \emph{fake} (e.g., due to model refusals or not following the prompt instructions).

\section{Benchmark Datasets}
\label{sec:datasets}

To evaluate how well the models generalise across different manipulation algorithms, subjects, and occlusion conditions, we use two video benchmarks for face swapping: \textbf{GOTCHA}~\cite{gotcha} and \textbf{FOWS} (\emph{Face Occlusion With Swapping})~\cite{fows}. In both, subjects perform physical actions that cover part of the face, producing frames that stress face swapping generators. Each frame is accordingly labelled as occluded (\texttt{occ}) or non-occluded (\texttt{no-occ}), depending on whether the hand or object covers the face.

\subsection{Source Datasets}

\paragraph{GOTCHA.}
GOTCHA~\cite{gotcha}, introduced by Mittal et al., is a benchmark for challenge-response detection of real-time deepfakes, in which subjects perform prescribed actions that expose the limitations of live face swapping pipelines. It contains recordings of 47 subjects performing eight challenges grouped into four categories: head movement, face occlusion, facial deformation, and face illumination, with swaps available from three generators. Following Ziglio et al.~\cite{fows}, we use the hand and object occlusion challenges and the swaps produced by DeepFaceLab~\cite{deepfacelab} and FSGAN (v2)~\cite{fsgan}.

The 47 subjects are partitioned into 30 for training and 17 for testing, with no subject appearing in both sets as either source or target identity. All evaluation uses the 17-subject \textbf{test partition}; the 30 training subjects serve only as the few-shot demonstration pool (\Cref{sec:few_shot_method}). Over the hand and object occlusion challenges, the test partition comprises \num{68899} frames (\num{36236} real and \num{32663} fake).

\paragraph{FOWS.}
FOWS (Face Occlusion With Swapping) is a dataset collected by Ziglio et al.~\cite{fows} at Fondazione Bruno Kessler (FBK). It focuses on the face occlusion setting, which prior work identified as the most effective at revealing face swapping artifacts in remote video communication. Each clip shows a subject who, on request, occludes their own face either with their hand (hand occlusion challenge) or with a supplied rectangular object (object occlusion challenge) at predefined positions.

Recording was driven by a guiding video overlaid on the camera feed that indicated where to place the face and the occluder. For each challenge they defined three variants with different occluder trajectories, for six guiding videos of about 40 seconds. Every clip starts with a static segment showing the face without occlusion and continues with a dynamic segment of roughly 15 seconds in which the occluder moves across the face. Seven subjects each recorded the six variants, giving 42 genuine clips.

For each genuine recording, manipulated counterparts were produced with three generators that swap faces from a single target image, SimSwap~\cite{simswap}, GHOST~\cite{ghost}, and FaceDancer~\cite{facedancer}, using royalty-free celebrity photographs as target identities. A fourth generator, DLC, was added after publication and is not described in the paper.
% TODO: add citation and full name for DLC once located.

In total, FOWS provides \num{42000} frames over the seven subjects, evenly split between occluded and non-occluded frames. Five subjects form the training pool used for few-shot demonstrations (\Cref{sec:few_shot_method}); the remaining two form the \textbf{test partition}, a deliberately challenging split of the only female subject and the only male subject with a thick beard. The test partition contains \num{12000} frames (\num{2400} real and \num{9600} fake), a $1:4$ ratio of real to fake frames obtained by pairing each genuine frame with its four swaps.

This guarantees deterministic dependency resolution across installations.

\section{Inference Engine Selection}
\label{sec:engine}

The benchmark requires a prediction for every frame in the test partitions, more than \num{80000} in total, and this is repeated for each candidate configuration. Processing a workload of this size makes the inference engine a central choice, since it governs how efficiently the GPU is used.

We adopted vLLM~\cite{vllm}, an inference engine built for high-throughput generation. It offers three properties that match our setting. It performs \emph{continuous batching}: instead of waiting for a whole batch of requests to finish before starting the next, it fills each freed slot with a waiting request as soon as the current one completes, so the GPU stays busy rather than idling on requests that have already finished. It supports a wide range of models directly from the Hugging Face ecosystem, together with several quantization formats, which is what makes the model suite of \Cref{sec:models} feasible on a single card. And it provides mature multi-GPU support, useful for portability even though our experiments use one GPU.

vLLM can be used in two ways: as an online server exposing an HTTP endpoint, or as a library called directly from Python for offline batch inference. The online server targets interactive, chatbot-style applications where requests arrive over time. Our workload is the opposite: a fixed, known set of frames processed in bulk with no external clients. We therefore use the offline mode, which removes the HTTP layer and its serialisation overhead, avoids the operational burden of running and monitoring a server, and lets the pipeline of \Cref{sec:pipeline} drive generation as ordinary function calls.

\section{Model Set}
\label{sec:models}

This section presents the full set of models we evaluate. We benchmark openly available models rather than proprietary ones served behind an API. The datasets consist of facial images of identifiable subjects, and sending them to an external service would expose that personal data outside our control. Running openly available models on our own hardware keeps every image local and avoids this exposure.

Candidate models were drawn from the Hugging Face ecosystem and admitted to the set under three constraints. Each model must (i) be able to process images and have been tuned to follow instructions, (ii) be supported by the vLLM engine of \Cref{sec:engine}, and (iii) fit within the \num{80}\,GB of a single A100 (\Cref{sec:compute_env}) together with the memory it needs at run time, since no parallelism across GPUs is used. This run-time memory is dominated by the key-value cache (KV cache) that the model accumulates as it generates, and it grows with the context length and the batch size. The resulting set of nine models is listed in \Cref{tab:models}. It deliberately spans a wide range of scales and architectural families, from a compact \num{5.6}\,B dense model to a \num{109}\,B mixture of experts (MoE), a sparse design that activates only a small fraction of its parameters per token.

\paragraph{Precision and quantisation.}
At native 16 bit precision a model stores roughly two bytes per parameter for its weights, and the KV cache introduced above adds further memory on top. Eight of the nine models fit within \num{80}\,GB at their native \texttt{bf16} precision. The exception is Llama-4-Scout, whose \num{109}\,B parameters would need well over \num{200}\,GB in 16 bit form. We therefore use a community \texttt{w4a16} checkpoint that stores the weights in 4 bits while keeping activations at 16 bits, cutting the weight footprint by roughly four times. For the largest models the context length was capped to the maximum vLLM reports as fitting once the weights are loaded: \num{44480} tokens for gemma-4-31B-it and \num{64816} for Llama-4-Scout.

\paragraph{Reasoning models.}
Some of these models are hybrids that can produce a chain of reasoning before their final answer that we enable or disable according to the task objectives.

\section{Evaluation Metric}
\label{sec:metric}

The primary metric on which models, prompts, and datasets are compared throughout this work is the Matthews Correlation Coefficient (MCC). Reusing the confusion matrix counts over the binary label space of \Cref{sec:formulation}, with \emph{fake} as the positive class and \emph{real} as the negative class, let $\mathrm{TP}$, $\mathrm{TN}$, $\mathrm{FP}$, and $\mathrm{FN}$ denote the true positives, true negatives, false positives, and false negatives. MCC is defined as
\begin{equation}
	\text{MCC} = \frac{\mathrm{TP}\cdot\mathrm{TN} - \mathrm{FP}\cdot\mathrm{FN}}{\sqrt{(\mathrm{TP}+\mathrm{FP})(\mathrm{TP}+\mathrm{FN})(\mathrm{TN}+\mathrm{FP})(\mathrm{TN}+\mathrm{FN})}} ,
	\label{eq:mcc}
\end{equation}
and takes values in $[-1, 1]$: $+1$ for perfect agreement between prediction and ground truth, $0$ for predictions no better than chance, and $-1$ for total disagreement. Whenever any factor in the denominator is zero, which happens when the model assigns every frame to a single class, the coefficient is taken to be $0$.

We take MCC as the primary metric on the grounds established by Chicco and Jurman~\cite{mcc}, who show it to be more informative and truthful than accuracy and the F1 score for binary classification. MCC is the only one of these common scalar summaries that draws on all four cells of the confusion matrix, so it yields a high value only when the classifier predicts both the real and the fake class well, proportionally to the number of real and fake instances in the data. Accuracy and F1, by contrast, can be overoptimistically inflated on class-imbalanced datasets by a classifier that favours the majority class. This distinction is material here because the full test partitions are imbalanced: FOWS pairs each genuine frame with four swaps, a $1{:}4$ real-to-fake ratio (\Cref{tab:datasets}), so a detector that labels every frame \emph{fake} would reach $80\%$ accuracy while learning nothing, yet its MCC is $0$. MCC is furthermore symmetric: it is invariant to swapping which class is designated positive, so the reported score does not depend on the arbitrary choice of treating \emph{fake} rather than \emph{real} as the positive class, unlike the F1 score.

A prediction of the failure symbol $\bot$ (\Cref{sec:formulation}) is scored as an incorrect answer rather than discarded, as in FakeBench~\cite{fakebench}. Before \Cref{eq:mcc} is evaluated we assign it the label opposite to the ground truth, so a $\bot$ counts as a false positive on a real frame and a false negative on a fake one. This keeps every frame in the evaluation, so a model that fails to answer is not implicitly rewarded by having those frames removed from its score.

\section{Pipeline Architecture}
\label{sec:pipeline}

\subsection{Overview}
\label{subsec:pipeline_overview}

Evaluating nine MLLMs (\Cref{sec:models}) across tens of thousands of video frames under hundreds of prompt variations requires an automated and robust evaluation framework. Managing a benchmark of this scale on a single 80\,GB accelerator (\Cref{sec:compute_env}) presents three primary challenges:
\begin{enumerate}
    \item \textbf{Experiment Configuration and Tracking:} Combining hundreds of prompts with nine models and multiple datasets results in thousands of evaluation runs. Configuring these manually is prone to errors, so the system requires declarative, version controlled configurations to automate these runs and reliably track all metadata for downstream analysis.
    \item \textbf{Task Extendability:} Because the experimental methodology evolved progressively as new tasks were designed, the architecture must be easily extendable.
    \item \textbf{Inference Engine Flexibility:} The pipeline must allow different inference backends to be plugged in without changing the evaluation workflow.
\end{enumerate}

To address these requirements, we developed a modular, configuration driven pipeline implemented in Python 3.12, based on an extensible registry architecture. At runtime, execution follows an automated lifecycle. The pipeline reads a declarative study plan and expands the requested models, datasets, prompts, and other configurations into a matrix of independent execution units. To maximize GPU efficiency, these units are grouped by model and dispatched sequentially to isolated worker processes. Inside each worker, images are loaded with their associated metadata, formatted into multimodal prompt requests, and sent in batches to the inference provider. The raw textual outputs from the model are then extracted by a deterministic response parser and streamed directly to disk as structured, append only records.

\subsection{Declarative Configuration}
\label{subsec:declarative_configuration}

In many evaluation pipelines, experiments are defined through hardcoded python scripts or long lists of command line arguments. These approaches leave no structured record of the experimental setup and make reproducing runs difficult. To ensure transparency, reproducibility, and version control, our pipeline defines all experiments through human readable TOML configuration files.

To avoid repeating model definitions across different experiments, configurations are separated into two distinct layers:
\begin{enumerate}
    \item \textbf{Shared Model Configurations (\emph{How to interact with a model}):} Each model has a single, reusable configuration file stored in \texttt{shared\_configs/models/}. This file defines how to communicate with the inference engine and passes all necessary runtime arguments to instantiate and serve the model. Supported parameters include, for example, the backend engine (such as vLLM or an external API), the model source on Hugging Face, data type precision, maximum context window size, optional LoRA adapters, and custom chat templates.
    \item \textbf{Study Configurations (\emph{What experiment to run}):} We use the term \emph{study} to refer to a structured experiment designed to evaluate a specific task, such as zero shot classification or few shot in context learning. Rather than creating dozens of separate, repetitive configuration files for each individual combination of model, prompt, and dataset, a study TOML declares all target models, datasets, prompt collections, batch sizes, and sampling settings together in one place. These are stored under the \texttt{studies/} directory, divided into task specific folders such as \texttt{zero\_shot/} and \texttt{few\_shot/}.
\end{enumerate}

\Cref{lst:dir_structure} shows how these components are organized on disk. Under each study category, such as \texttt{zero\_shot/}, individual experiments are defined as dedicated TOML files (for example, \texttt{stage1.toml} or \texttt{stage2\_v3\_full.toml}) and are collocated with their corresponding prompt templates in \texttt{prompts/} and output logs in \texttt{results/}.

\subsection{Modular Registry Architecture}
\label{subsec:registry_architecture}

Because the evaluation tasks and experimental directions were designed and refined progressively throughout the research rather than being fully determined from the start, the evaluation framework required a flexible and modular architecture. To allow new experimental paradigms to be introduced without continuously modifying the core execution engine, the pipeline is built around a modular registry pattern.

Under this design, implementing a new component requires only writing a dedicated class or module and annotating it with the corresponding registration decorator, such as \texttt{@register\_task} or \texttt{@register\_provider}. At runtime, factory functions discover and instantiate the required components dynamically based on the declarative strings specified in the study TOML configuration. The pipeline exposes five concrete extension points:
\begin{enumerate}
    \item \textbf{Dataset Loaders (\texttt{@register\_data\_loader}):} Encapsulate benchmark specific disk layouts, partition splits, and metadata extraction. When testing new benchmarks in the future, researchers can simply add a new loader without having to convert or reorganise their dataset directory structures into a rigid format. Currently, three loaders are implemented:
    \begin{itemize}
        \item \texttt{fows\_loader} and \texttt{gotcha\_loader}: parse the distinct directory layouts of FOWS and GOTCHA respectively. Although the datasets organise files differently on disk, both loaders extract a consistent set of per frame metadata attributes: dataset split, manipulation generator, subject identifier (\texttt{user\_id}), occlusion challenge, and occlusion category (\texttt{occ} or \texttt{no-occ}).
        \item \texttt{simple\_image\_loader}: loads images organised into two basic subfolders, \texttt{real} and \texttt{fake}, for simple evaluations that do not require detailed metadata.
    \end{itemize}
    
    \item \textbf{Response Parsers (\texttt{@register\_response\_parser}):} Implement the deterministic extraction policy $\pi(t)$ (\Cref{sec:formulation}) to map free text model outputs to binary predictions. Currently, two parsers are implemented:
    \begin{itemize}
        \item \texttt{single\_phrase}: scans the text using regular expressions to find occurrences of the designated real or fake target words (such as \texttt{authentic} or \texttt{faceswapped}). It extracts either the first or last matched keyword according to the prompt configuration, mapping it to \texttt{real} or \texttt{fake}, or emitting a parse failure if neither word appears.
        \item \texttt{verdict}: handles structured outputs by searching for a specified prefix delimiter (such as \texttt{Verdict:}) followed by the target word, extracting the final decision that follows the delimiter.
    \end{itemize}
    
    \item \textbf{Study Parsers (\texttt{@register\_study\_parser}):} Read declarative study TOML files, expand their configurations into a collection of concrete execution units, and group them by model. Currently, two study parsers are implemented:
    \begin{itemize}
        \item \texttt{standard}: performs a combinatorial matrix expansion across all declared models, datasets, prompt files, and sampling parameters for zero-shot studies.
        \item \texttt{few\_shot}: parses few-shot study configurations, managing demonstration pools, exemplar counts, composition rules, and exemplar ordering strategies.
    \end{itemize}
    If a future experiment requires a completely different execution layout or experimental structure, it can be supported simply by registering a new study parser.

    \item \textbf{Tasks (\texttt{@register\_task}):} Implement the execution workflow and prompt assembly for an experiment. Each task builds the multimodal message payload for each query image (such as pairing an image with text instructions in \texttt{zero\_shot}, or prepending demonstration images and their corresponding labels in \texttt{few\_shot}), submits batches to the inference provider, and saves the parsed predictions to disk.

    \item \textbf{Inference Providers (\texttt{@register\_provider}):} Implement the communication with the underlying inference engine according to the properties declared in the shared model TOML configuration. Currently, the provider is implemented for local offline \texttt{vllm} execution (\Cref{sec:engine}).
\end{enumerate}

\subsection{GPU Memory Isolation}
\label{subsec:vram_isolation}

Evaluating nine large multimodal models (\Cref{sec:models}) on a single 80\,GB accelerator (\Cref{sec:compute_env}) introduces a strict memory management challenge. Large models occupy a substantial fraction of the available VRAM for their parameter weights, with remaining memory allocated to continuous key-value cache pools. Crucially, inference engines such as vLLM are designed for persistent serving and expose no internal Python API to completely unload a resident model or free its allocated cache memory. Executing multiple models sequentially within a single persistent process causes residual memory accumulation that quickly leads to out of memory errors.

To overcome this limitation while maintaining high throughput, the pipeline applies two complementary strategies:

\paragraph{Model Centric Execution Grouping.}
A naive execution loop over prompts or datasets would repeatedly reload multi gigabyte model weights for every prompt variation, creating immense initialization overhead. The study parser instead partitions the expanded execution matrix into model centric groups. All prompts, datasets, and configurations targeting a given model are processed in a single continuous pass, ensuring that model weights are transferred to the accelerator only once per study.

\paragraph{Subprocess Isolation per Model.}
To guarantee complete VRAM reclamation between successive models, the orchestrator executes each model group inside a fresh, isolated worker subprocess using the Python \texttt{multiprocessing} library. The worker process initializes the model, runs all assigned evaluation units, and writes predictions directly to disk. Once the group finishes, the worker process terminates completely. The operating system and GPU driver automatically release all allocated GPU memory, guaranteeing a clean memory state before the orchestrator launches the worker for the next model.

\subsection{Resumability, Fault Tolerance, and Metadata Preservation}
\label{subsec:resumability_provenance}

Running large scale benchmarks across tens of thousands of frames requires mechanisms to recover gracefully from interruptions, isolate runtime failures, and preserve complete records for downstream analysis.

\paragraph{Resumability.}
To eliminate the cost of restarting interrupted experiments, model predictions are streamed incrementally to disk as append only JSON Lines (JSONL) files. A dedicated \texttt{StateManager} tracks processed items by their unique image paths. When an experiment resumes after an interruption, the worker queries the state manager and skips already completed images. Furthermore, if all items in an execution unit have already been processed, the orchestrator skips that unit entirely before the model is even loaded into GPU memory.

\paragraph{Fault Tolerance.}
To prevent runtime anomalies or unexpected input failures from blocking the entire benchmark, the worker tracks consecutive inference errors. If errors occur repeatedly and exceed a predefined threshold of ten consecutive failures, the worker terminates that specific model group while allowing the orchestrator to proceed cleanly with the remaining models in the study.

\paragraph{Metadata Preservation.}
Every emitted JSONL record preserves the complete per frame metadata alongside the raw model output text and the parsed prediction. Retaining these attributes directly with the predictions enables the fine grained comparative breakdowns presented in \Cref{chap:results}, such as evaluating detection performance across specific generators and occlusion conditions.

\subsection{Sampling and Determinism}
\label{subsec:sampling_determinism}

To ensure that the benchmark measures the intrinsic capabilities of each model rather than stochastic sampling variance, all experiments are conducted using greedy decoding with sampling temperature set to zero ($\tau = 0.0$). 

While setting temperature to zero instructs the model to select the token with the highest probability at each step, greedy decoding on modern GPUs does not guarantee strict bit level reproducibility across different execution settings. As shown by Yuan et al.~\cite{yuan2025nondeterminism}, the non associative nature of floating point addition in parallel GPU reduction kernels, combined with dynamic request scheduling in continuous batching, introduces slight numerical variations in computed logits. When the probability gap between candidate tokens is narrow, these small rounding differences can occasionally flip token selection. This effect was observed during our single exemplar few-shot experiments ($n = 1$), where identical prompt content yielded minor token level variations under different batch scheduling orders (\Cref{sec:few_shot_method}).

\section{Staged Zero-Shot Prompt Engineering}
\label{sec:staged_prompting}

Evaluating the intrinsic forensic capabilities of Multimodal Large Language Models requires carefully designed prompts. However, as formulated in \Cref{sec:formulation}, a prompt is not a monolithic string but a structured combination of distinct components: the target label vocabulary $\mathcal{V}$, contextual task definitions $\mathcal{S}$, domain personas $\mathcal{R}$, and reasoning modes $\mathcal{C}$. In a zero-shot setting where no labeled exemplars are provided ($\mathcal{D} = \emptyset$), the prompt space is defined by the tuple:
\begin{equation}
    p = \langle \mathcal{V}, \mathcal{S}, \mathcal{R}, \mathcal{C}, \emptyset \rangle
\end{equation}

Jointly exploring all possible combinations of nine candidate models, 28 vocabulary pairs, multiple structural templates, six expert personas, and diverse reasoning modes across the full test partitions (exceeding \num{80000} frames) would require millions of inference queries. On a single accelerator (\Cref{sec:compute_env}), an exhaustive combinatorial grid search across all dimensions simultaneously is computationally intractable.

To make this exploration tractable, we design a staged prompt engineering funnel that isolates and optimizes one orthogonal dimension of the prompt tuple at a time on the balanced development set (\Cref{sec:datasets}):
\begin{enumerate}
    \item \textbf{Stage 1 (Vocabulary Search $\mathcal{V}$):} Evaluates a grid of 28 candidate word pairs across all nine models using a minimal prompt, identifying the optimal target vocabulary for each model and down-selecting the model suite to the five top performers (\Cref{subsec:stage1_vocabulary}).
    \item \textbf{Stage 2 (Structural Context $\mathcal{S}$ and Persona $\mathcal{R}$):} Explores nine structural templates placing definitions, task descriptions, and domain personas in system versus user message roles, evaluating each of the five selected models exclusively with its Stage~1 winning vocabulary (\Cref{subsec:stage2_structure}).
    \item \textbf{Stage 3 (Reasoning Mode $\mathcal{C}$):} Evaluates unguided Chain-of-Thought, a guided forensic cue checklist, and answer-first reasoning on each model's winning Stage~2 prompt template (\Cref{subsec:stage3_reasoning}).
\end{enumerate}

\subsection{Prompt Architecture and Funnel Rationale}
\label{subsec:prompt_funnel_rationale}

\paragraph{Declarative Prompt Template Schema.}
Within the evaluation pipeline (\Cref{sec:pipeline}), every prompt is defined as a declarative JSON document that decouples conversation structure from image assets and extraction rules. As shown in \Cref{lst:prompt_schema}, a prompt template contains three primary fields:
\begin{enumerate}
    \item \texttt{id}: A unique identifier declaring the template format (for example, \texttt{basic\_conversation\_v1} for direct zero-shot queries or \texttt{cot\_conversation\_v1} for reasoning variants).
    \item \texttt{conversations}: An ordered list of message objects specifying the conversation turn (\texttt{system} or \texttt{user}) and its content blocks. Text blocks provide instructions, while image blocks contain logical placeholders (\texttt{image\_id: "target\_image"}) that the task worker dynamically populates with the queried frame.
    \item \texttt{response\_format}: Specifies the extraction contract parsed by $\pi(t)$ (\Cref{sec:formulation}). For single-phrase classification, it declares the expected target label words $w_{\text{real}}$ and $w_{\text{fake}}$.
\end{enumerate}

\begin{lstlisting}[basicstyle=\ttfamily\scriptsize,breaklines=true,frame=single,caption={Declarative JSON template schema for a minimal zero-shot prompt.},label={lst:prompt_schema}]
{
  "id": "basic_conversation_v1",
  "conversations": [
    {
      "role": "user",
      "content": [
        {
          "type": "image",
          "image_id": "target_image"
        },
        {
          "type": "text",
          "text": "Is the face in this image authentic or fake? Answer with exactly one phrase: 'authentic' or 'fake'."
        }
      ]
    }
  ],
  "response_format": {
    "type": "single_phrase",
    "real_word": "authentic",
    "fake_word": "fake"
  }
}
\end{lstlisting}

\paragraph{Greedy Funnel Optimization and Methodological Trade-offs.}
The staged search implements a greedy heuristic along the orthogonal components of the prompt parameter space. By optimizing $\mathcal{V}$ first, fixing the winning vocabulary per model, and subsequently exploring $\mathcal{S}$, $\mathcal{R}$, and $\mathcal{C}$, the total number of evaluation runs is reduced by several orders of magnitude.

This greedy decomposition involves a clear methodological trade-off. It assumes that vocabulary preference remains relatively stable across different prompt structures. A specific model could theoretically perform better with a particular persona or definition when paired with an alternative vocabulary pair that was eliminated during Stage~1. However, because a joint grid search across the full Cartesian product is computationally prohibitive, this staged heuristic provides a principled, reproducible framework for exploring prompt variations within feasible compute budgets.

\paragraph{Evaluation on the Balanced Development Set.}
To prevent computational bottlenecks, all intermediate decisions across Stages~1, 2, and 3 are evaluated on the balanced development sets of FOWS and GOTCHA (\num{1344} frames each, \Cref{subsec:devset}). Candidate configurations are selected using the Matthews Correlation Coefficient (\Cref{sec:metric}) on these development sets. Only the winning configurations identified through this funnel are subsequently evaluated across the full benchmark test partitions.

\subsection{Stage 1: Target Class Vocabulary Search and Model Selection}
\label{subsec:stage1_vocabulary}

\paragraph{Vocabulary Grid Design.}
In binary classification with natural language models, the specific words assigned to the positive and negative classes can significantly alter model predictions. As demonstrated by Ismithdeen et al.~\cite{ismithdeen2025promptception}, Multimodal Large Language Models exhibit substantial lexical sensitivity, where subtle shifts in prompt vocabulary produce performance swings of up to \num{15}\% to \num{50}\% across vision benchmarks. Standard labels such as \texttt{"real"} and \texttt{"fake"} are semantically broad and carry priors from general pretraining that may not align well with visual manipulation artifacts. To identify the optimal terminology for face swap detection, Stage 1 systematically evaluates candidate vocabulary words along both class dimensions:
\begin{itemize}
    \item \textbf{Real class ($w_{\text{real}}$, 4 candidates):} \texttt{authentic}, \texttt{bona fide}, \texttt{original}, \texttt{real}.
    \item \textbf{Fake class ($w_{\text{fake}}$, 7 candidates):} \texttt{fake}, \texttt{deepfake}, \texttt{generated}, \texttt{faceswapped}, \texttt{manipulated}, \texttt{synthetic}, \texttt{modified}.
\end{itemize}
Taking the Cartesian product yields $4 \times 7 = 28$ candidate vocabulary pairs.

To isolate the effect of word choice from other prompt factors, each pair is embedded into a minimal, zero shot prompt template without personas or explanatory definitions:
\begin{quote}
    \emph{Is the face in this image $w_{\text{real}}$ or $w_{\text{fake}}$? Answer with exactly one phrase: '$w_{\text{real}}$' or '$w_{\text{fake}}$'.}
\end{quote}

\paragraph{Output Format Rationale.}
Rather than requiring models to follow a rigid prefix structure (such as \texttt{"Verdict: fake"}), or structured formats such as JSON or XML, the prompt instructs the model to directly emit the selected class phrase. In empirical studies on prompt formatting, Ismithdeen et al.~\cite{ismithdeen2025promptception} observed that imposing rigid formatting constraints, complex schemas, or non-negotiable answer headers on open weights models caused severe accuracy drops of \num{15}\% to \num{23}\%. The deterministic parser $\pi(t)$ (\Cref{sec:formulation}) directly extracts the target phrase using regular expressions, recording a failure symbol $\bot$ if neither word appears.

\paragraph{Evaluation and Model Selection.}
All 28 vocabulary pairs were evaluated across the complete suite of nine models (\Cref{sec:models}) on both the FOWS and GOTCHA balanced development sets (\num{1344} frames each), resulting in 504 individual evaluation units and \num{677376} inference requests.

To jointly assess performance across both manipulation benchmarks, we define the overall evaluation score as the arithmetic mean of the MCC scores computed on each development set:
\begin{equation}
    \text{MCC}_{\text{overall}} = \frac{\text{MCC}_{\text{FOWS}} + \text{MCC}_{\text{GOTCHA}}}{2}
    \label{eq:mcc_overall}
\end{equation}

Because running subsequent prompt engineering stages across all nine models would multiply the experimental volume beyond computational constraints, Stage 1 serves as a selection filter. For each model, candidate vocabulary pairs were ranked by $\text{MCC}_{\text{overall}}$, identifying the model's optimal word pair. Models were then ranked according to their peak overall MCC score. The top five models were chosen for subsequent exploration:
\begin{enumerate}
    \item \texttt{Qwen/Qwen3.6-35B-A3B}
    \item \texttt{Qwen/Qwen3.6-27B}
    \item \texttt{google/gemma-4-31B-it}
    \item \texttt{moonshotai/Kimi-VL-A3B-Instruct}
    \item \texttt{RedHatAI/Llama-4-Scout-17B-16E-Instruct-quantized.w4a16}
\end{enumerate}
The remaining four models (\texttt{GLM-4.6V-Flash}, \texttt{Nemotron-Nano-12B}, \texttt{InternVL3.5-30B}, and \texttt{Phi-4-multimodal}) exhibited lower peak performance and were excluded from subsequent stages.

Evaluating the candidate pairs on the development sets yields the winning vocabulary pair for each of the five selected models, summarized in \Cref{tab:stage1_winners}. These winning pairs define the fixed target vocabulary $\mathcal{V}$ for each model in Stage 2. A detailed comparative analysis of lexical sensitivity across the full 28 pair grid is presented in \Cref{chap:results}.

\subsection{Stage 2: Structural Context and Persona Engineering}
\label{subsec:stage2_structure}

\paragraph{Contextual Elements: Definitions and Task Descriptions.}
While Stage 1 identified the optimal class vocabulary $\mathcal{V}$, Stage 2 evaluates how contextual task framing $\mathcal{S}$ and domain expert personas $\mathcal{R}$ influence classification performance. We define two distinct categories of contextual instructions:
\begin{enumerate}
    \item \textbf{Semantic Definitions ($\mathcal{S}_{\text{def}}$):} Provide explicit semantic boundaries explaining the physical distinction between real and fake faces in face swapping:
    \begin{quote}
        \emph{An '$w_{\text{real}}$' face belongs to the person originally photographed. A '$w_{\text{fake}}$' face belongs to a different person and has been placed into [the/this] image using faceswapping techniques.}
    \end{quote}
    \item \textbf{Task Descriptions ($\mathcal{S}_{\text{task}}$):} State the forensic objective as an imperative instruction without defining the individual vocabulary words:
    \begin{quote}
        \emph{Your task is to determine whether the face in [a given/this] image belongs to the person originally photographed, or belongs to a different person and has been placed into [the/this] image using faceswapping techniques.}
    \end{quote}
\end{enumerate}

\paragraph{Structural Placement Templates.}
To evaluate whether contextual directives are more effective when placed globally in the system message or provided locally alongside the query image in the user message, we construct nine structural templates, summarized in \Cref{tab:stage2_structures}:
\begin{itemize}
    \item \texttt{1\_def\_sys}: Semantic definitions placed in the system message, with the query image and question in the user message.
    \item \texttt{2\_def\_usr}: Semantic definitions placed directly in the user message alongside the query, with no system message.
    \item \texttt{3\_task\_sys}: Task descriptions placed in the system message, with the query image and question in the user message.
    \item \texttt{4\_task\_usr}: Task descriptions placed directly in the user message alongside the query, with no system message.
    \item \texttt{5\_persona\_only}: An expert persona assigned in the system message, without supplementary definitions or task framing.
    \item \texttt{6\_persona\_sys\_def\_sys}: An expert persona combined with semantic definitions in the system message.
    \item \texttt{7\_persona\_sys\_def\_usr}: An expert persona in the system message, with semantic definitions placed in the user message.
    \item \texttt{8\_persona\_sys\_task\_sys}: An expert persona combined with task descriptions in the system message.
    \item \texttt{9\_persona\_sys\_task\_usr}: An expert persona in the system message, with task descriptions placed in the user message.
\end{itemize}

\paragraph{Domain Expert Personas.}
For structural templates that include a persona role (templates $5$ through $9$), we define six domain specific personas $\mathcal{R} = \{P_1, \dots, P_6\}$ covering forensic analysis, media moderation, and technical imaging domains:
\begin{itemize}
    \item $P_1$ (\textbf{Deepfake Specialist}): \emph{You are an expert specializing in deepfake detection and facial manipulation analysis.}
    \item $P_2$ (\textbf{Forensic Examiner}): \emph{You are a forensic image examiner with expertise in detecting digital tampering in photographic evidence.}
    \item $P_3$ (\textbf{Visual Effects Artist}): \emph{You are a professional visual effects artist experienced in creating realistic face composites for film production.}
    \item $P_4$ (\textbf{Biometric Analyst}): \emph{You are a biometric verification analyst working in identity fraud prevention.}
    \item $P_5$ (\textbf{Computer Vision Researcher}): \emph{You are a computer vision researcher specializing in face analysis and generative model artifacts.}
    \item $P_6$ (\textbf{Content Integrity Analyst}): \emph{You are a content integrity analyst responsible for detecting manipulated media on a social platform.}
\end{itemize}
Across the nine structural templates, templates 1 to 4 yield one prompt each, while templates 5 to 9 are crossed with all six personas ($5 \times 6 = 30$ prompts), resulting in 34 prompt configurations per model.

\paragraph{Experimental Protocol and Model Selection.}
Stage 2 evaluates each of the five selected models exclusively with its Stage 1 winning vocabulary pair across all 34 structural prompt variations on the balanced development sets of FOWS and GOTCHA.

For each model, the 34 prompt variations were ranked according to $\text{MCC}_{\text{overall}}$ (\Cref{eq:mcc_overall}) to determine its optimal structural configuration. Based on their peak performance in Stage 2, the model suite was further narrowed to the top three models: \texttt{Qwen/Qwen3.6-35B-A3B}, \texttt{google/gemma-4-31B-it}, and \texttt{Qwen/Qwen3.6-27B}. These three models were evaluated with their winning prompt structures on the full benchmark test partitions and carried forward to the reasoning evaluations in Stage 3. Detailed comparative breakdowns and empirical comparisons across prompt structures are reported in \Cref{chap:results}.

\subsection{Stage 3: Reasoning Modes}
\label{subsec:stage3_reasoning}

\paragraph{Objective and Explainability Rationale.}
Beyond assessing classification accuracy, a critical objective of this benchmark is to evaluate forensic explainability by examining whether Multimodal Large Language Models can explicitly articulate the visual reasoning behind their decisions. In digital forensics, a binary verdict without justification provides limited utility for verification. Stage 3 investigates whether eliciting visual reasoning enables models to identify and describe manipulation traces, while simultaneously evaluating whether generating reasoning tokens improves classification accuracy over direct classification.

Rather than redesigning prompts from scratch, Stage 3 is constructed as a minimal extension of the winning Stage 2 configurations for the three carried forward models: the winning vocabulary $\mathcal{V}$, system message, and persona $\mathcal{R}$ remain unchanged, modifying only the instruction tail of the user message.

\paragraph{Reasoning Configurations.}
We evaluate three distinct reasoning configurations $\mathcal{C}$:
\begin{enumerate}
    \item \textbf{Unguided CoT:} Instructs the model to freely describe its observations and articulate its reasoning before stating the final verdict:
    \begin{quote}
        \emph{Is the face in this image $w_{\text{real}}$ or $w_{\text{fake}}$? First, briefly explain what you see and your reasoning. Then answer with exactly one phrase: '$w_{\text{real}}$' or '$w_{\text{fake}}$'.}
    \end{quote}
    \item \textbf{Guided CoT:} To provide explicit visual guidance on where to look for manipulation traces, this configuration presents the model with a structured checklist of telltale forensic cues across the face. In existing forensics literature, reasoning prompts frequently incorporate generic whole image synthesis cues, such as irregular background geometry, malformed hands, or strange hair textures~\cite{jia2024can}. While suitable for full image generation where every pixel is synthesized from noise, these cues are largely irrelevant to face swapping, where key surrounding context such as the background, torso, hands, ears, and outer hair remains completely authentic from the original camera capture.
    
    We therefore construct a targeted checklist tailored specifically to localized face swapping traces. In particular, because our benchmarks evaluate face swapping under physical obstructions where hands or objects pass in front of the face, we include a dedicated occlusion cue to detect the resulting boundary blending, texture fusion, and unnatural transparency artifacts:
    \begin{quote}
        \emph{Is the face in this image $w_{\text{real}}$ or $w_{\text{fake}}$? Look for clues in and around the face. Check each point below. For each, say "normal" unless you can point to a specific problem you actually see in the image; describe exactly what it is and where. Do not infer a problem you cannot directly see.}
        \begin{itemize}
            \item \textbf{Boundary:} the edge where the face meets the hairline, ears, jaw, and neck. Look for a hard cut out outline, a ring of blur, or one part looking sharper, blurrier, or a different color than the skin right next to it.
            \item \textbf{Skin:} the color and texture of the face compared with the neck and ears. Look for the face being lighter, darker, or more waxy and over smooth than the surrounding skin.
            \item \textbf{Lighting:} the direction of light and the shadows on the face compared with the rest of the image. Look for light or shadows on the face that fall the wrong way or don't match the rest of the image.
            \item \textbf{Eyes and teeth:} the eyes, and the teeth if visible. Look for missing or blurred eyelashes, the bright reflections in the two eyes not matching, oddly shaped pupils, or smeared or malformed teeth.
            \item \textbf{Fit:} how well the face sits on the head. Look for features that are out of place, or a face that is the wrong size or shape for the head.
            \item \textbf{Occlusion:} a hand or object passing in front of the face. Look for a blurred or smeared boundary between them, the object and face appearing fused together, the skin color spreading onto the object, or the object looking partly transparent or warped instead of solidly in front.
        \end{itemize}
        \emph{Then answer with exactly one phrase: '$w_{\text{real}}$' or '$w_{\text{fake}}$'.}
    \end{quote}
    \item \textbf{Answer First:} In standard CoT prompting (Unguided and Guided CoT), generated reasoning tokens precede and autoregressively condition the final verdict. This introduces the risk of hallucination drift or error accumulation, where intermediate mistakes in the reasoning trace cause the model to deviate from an initially correct visual impression. To evaluate whether generating reasoning first actively assists or distracts the model from making a correct decision, Answer First instructs the model to state its binary decision immediately, conditioned solely on the input image, and generate its explanation afterwards:
    \begin{quote}
        \emph{Is the face in this image $w_{\text{real}}$ or $w_{\text{fake}}$? First, answer with exactly one phrase: '$w_{\text{real}}$' or '$w_{\text{fake}}$'. Then briefly explain what you see and the reasoning behind your answer.}
    \end{quote}
\end{enumerate}

\paragraph{Experimental Protocol.}
All three reasoning configurations were evaluated across the three selected models on the balanced development sets of FOWS and GOTCHA. Because reasoning traces increase generation length, the maximum token budget was raised from \num{512} to \num{1024} tokens for Stage 3 evaluation. The deterministic parser $\pi(t)$ extracts the final class phrase using regular expression pattern matching over the generated text. Full comparative results and qualitative trace analyses are reported in \Cref{chap:results}.

\section{Few Shot In Context Learning}
\label{sec:few_shot_method}

\subsection{Overview and Problem Formulation}
\label{subsec:fewshot_overview}

While the staged zero shot prompt engineering funnel (\Cref{sec:staged_prompting}) evaluates the baseline forensic sensitivity of Multimodal Large Language Models (MLLMs) under various contextual framings, it relies entirely on the pretrained parametric knowledge of each model. A central research question of this work is whether instruction tuned MLLMs can perform in context learning (ICL) in visual forensics: that is, whether providing labeled visual exemplars directly inside the context window enables models to better recognize subtle face swap manipulation artifacts without requiring parameter fine tuning.

In visual face swap detection, in context learning introduces distinct opportunities and challenges compared to pure text tasks. On one hand, showing the model example pairs of real and fake faces might help it recognize what face swap artifacts look like, such as blurry boundaries, unnatural skin tones, or blending artifacts. On the other hand, multimodal in context learning can introduce biases, including label frequency bias where the model predicts the majority demonstration class~\cite{baldassini2024whatmakes}, recency bias where the model repeats the label of the most recent exemplar~\cite{tan2024ordermatters,baldassini2024whatmakes,tian2025positionbias}, or performance drops where adding more demonstration images introduces noise and distracts the model from the task~\cite{dogan2026fewmmbench,qin2024whatfactors}.

\paragraph{Mathematical Task Formulation.}
We formulate few shot evaluation by re-engaging the prompt parameterization tuple defined in \Cref{sec:formulation}:
\begin{equation}
    p = \langle \mathcal{V}, \mathcal{S}, \mathcal{R}, \mathcal{C}, \mathcal{D} \rangle
\end{equation}
where $\mathcal{D} = \{(x_1^{(d)}, y_1^{(d)}), \dots, (x_n^{(d)}, y_n^{(d)})\}$ represents an ordered set of $n \ge 1$ labeled visual demonstration exemplars prepended to the target query image $x$. Each exemplar consists of an RGB facial image $x_i^{(d)}$ and its associated ground truth class label $y_i^{(d)} \in \{\text{real}, \text{fake}\}$.

\paragraph{Lineage and Baseline Control.}
To ensure that performance variations reflect solely the impact of visual demonstrations rather than confounding prompt modifications, all few shot prompts maintain strict lineage with the zero shot Stage~2 winning configurations (\Cref{subsec:stage2_structure}) for the top three evaluated models (\texttt{Qwen3.6-35B-A3B}, \texttt{google/gemma-4-31B-it}, and \texttt{Qwen3.6-27B}):
\begin{itemize}
    \item The target class vocabulary $\mathcal{V} = (w_{\text{real}}, w_{\text{fake}})$ is fixed to each model's winning Stage~1 word pair (\Cref{tab:stage1_winners});
    \item The system persona $\mathcal{R}$ and structural placement $\mathcal{S}$ are retained verbatim from each model's optimal Stage~2 prompt template;
    \item The reasoning mode is set to direct classification ($\mathcal{C} = \emptyset$), deliberately omitting the Chain of Thought reasoning from Stage~3 to isolate in context demonstration dynamics from autoregressive reasoning effects.
\end{itemize}
All few shot results are compared directly against the Stage~2 zero shot baseline on an image level paired basis across identical test partitions and sampling configurations ($\tau = 0.0$).

\subsection{Demonstration Pools and Exemplar Selection}
\label{subsec:fewshot_pools}

To provide visual exemplars for in context learning, we construct four dedicated demonstration pools based on the two benchmark datasets and their occlusion conditions:
\begin{enumerate}
    \item \texttt{fows\_occ}: 10 real and 10 fake frames from the FOWS occluded split;
    \item \texttt{fows\_noocc}: 10 real and 10 fake frames from the FOWS non-occluded split;
    \item \texttt{gotcha\_occ}: 10 real and 10 fake frames from the GOTCHA occluded split;
    \item \texttt{gotcha\_noocc}: 10 real and 10 fake frames from the GOTCHA non-occluded split.
\end{enumerate}
Each pool contains an equal number of real and fake images (10 pairs, 20 images total), allowing flexible assembly of balanced and unbalanced demonstration sequences. \Cref{tab:demo_pools} summarizes the composition of each pool.

\paragraph{Training Split Isolation.}
To prevent data leakage, all demonstration frames are sampled strictly from the designated training subjects of each benchmark: the five training subjects in FOWS and the 30 training subjects in GOTCHA. No frames or subjects from the evaluation test partitions appear in the demonstration pools.

\paragraph{Manual Exemplar Selection.}
All demonstration images were selected manually by hand. For the fake images in both the occluded and non occluded pools, we chose frames showing diverse artifacts and errors across different face swap generators. For the real images, we selected the original frames corresponding to those chosen fake images: in FOWS, this provides the exact real frame from the original recording of each swap, while in GOTCHA, where frame numbers do not directly match between real and swapped videos, the most similar real frame was selected.

\subsection{Experimental Sweep Dimensions}
\label{subsec:fewshot_dimensions}

To systematically examine how in context visual demonstrations influence model decisions, we define three experimental sweep dimensions: exemplar count, label composition, and ordering.

\paragraph{Demonstration Count ($n$).}
We evaluate five demonstration counts:
\begin{equation}
    n \in \{1, 2, 4, 6, 10\}
\end{equation}
Evaluating performance across varying demonstration counts allows us to observe whether face swap detection improves with more visual context, or whether performance saturates and degrades as additional images are added to the prompt.

\paragraph{Label Composition (Class Mix).}
To test how the balance and arrangement of labels affect model behavior, we evaluate four composition strategies:
\begin{enumerate}
    \item \texttt{all\_fake}: provides $n$ consecutive fake demonstrations. This tests whether the model learns visual indicators of face swaps from fake examples, or if it simply collapses into predicting the fake class for all queries.
    \item \texttt{all\_real}: provides $n$ consecutive real demonstrations. Similarly, this tests whether the model learns from real examples or simply defaults to predicting real.
    \item \texttt{interleave\_real\_first}: provides an alternating sequence of real and fake examples starting with a real image ($\text{real}, \text{fake}, \text{real}, \dots$). For even values of $n$, the sequence ends with a fake demonstration.
    \item \texttt{interleave\_fake\_first}: provides an alternating sequence starting with a fake image ($\text{fake}, \text{real}, \text{fake}, \dots$). For even values of $n$, the sequence ends with a real demonstration.
\end{enumerate}

\paragraph{Investigating Recency and Single Exemplar Priming.}
Testing interleaved sequences with both starting orders serves a specific analytical purpose. In an alternating sequence of length $n$, starting with real means the final demonstration immediately preceding the test query is fake, whereas starting with fake means the final demonstration is real. Comparing these two conditions helps isolate \emph{recency bias} (whether the model disproportionately repeats the label of the last demonstration it saw) versus \emph{primacy bias} (repeating the first demonstration).

Furthermore, evaluating $n = 1$ provides a direct baseline for single exemplar priming. By comparing $n = 1$ with longer interleaved sequences that end with the same label, we can determine whether the effect of the final demonstration in an interleaved sequence is simply equivalent to seeing a single demonstration of that class.

\paragraph{Sequential Ordering Strategy.}
For all evaluated conditions, demonstration images are drawn in a fixed, deterministic sequential order (\texttt{seq}) from the curated pools. For any chosen count $n$, the pipeline takes the exact $n$ element prefix from the corresponding ordered pool list. Using fixed sequential prefixes eliminates random sampling variance across runs, ensuring that performance differences across models and prompt settings stem strictly from the experimental variables rather than random exemplar selection.

\subsection{Prompt Construction and Runtime Configuration}
\label{subsec:fewshot_prompt_construction}

\paragraph{Single Turn Multi Image Formatting.}
In conversational Multimodal Large Language Models, prompts are typically handled as chat exchanges between a \texttt{user} and an \texttt{assistant}. When providing few shot demonstrations, there are two distinct ways to structure this conversation:
\begin{itemize}
    \item \textbf{Multi turn structure:} Each demonstration is represented as an alternating dialogue turn. The user provides an example image with the question, and we pre-fill the assistant's turn with the ground truth answer label in the conversation history (\texttt{user} $\to$ \texttt{assistant} $\to$ \texttt{user} $\to$ \dots). In this setup, the assistant responses in the demonstration history are not generated by the model at runtime, but are supplied by us as simulated turns, with the model generating an answer only when prompted with the final query test image.
    \item \textbf{Single turn structure:} All $n$ demonstration images, along with their questions and pre-filled ground truth answers, are placed together with the query test image inside a single \texttt{user} message.
\end{itemize}
Following standard multimodal in context learning protocols~\cite{dogan2026fewmmbench,qin2024whatfactors}, we adopt the single turn format across all our few shot evaluations. This allows the model to process all labeled visual examples as a continuous in context prefix within a single prompt before generating its final verdict.

\Cref{lst:fewshot_prompt_schema} illustrates the declarative JSON template schema used for few shot prompts. In this schema, the contiguous pair of \texttt{demo\_image} and \texttt{demo\_text} blocks serves as the template for a single demonstration.

\begin{lstlisting}[basicstyle=\ttfamily\scriptsize,breaklines=true,frame=single,caption={Declarative JSON template schema for a few shot single turn prompt.},label={lst:fewshot_prompt_schema}]
{
  "id": "few_shot_single_turn_v1",
  "baseline_prompt": "zero_shot/stage2/real_word_as_authentic/D_faceswapped/9_persona_sys_task_usr/P6_integrity_moderator.json",
  "conversations": [
    {
      "role": "user",
      "content": [
        { "type": "text", "text": "Your task is to determine whether the face in this image belongs to the person originally photographed, or belongs to a different person and has been placed into this image using faceswapping techniques.\n\n" },
        { "type": "image", "image_id": "demo_image" },
        { "type": "text", "text_id": "demo_text", "text": "Is the face in this image authentic or faceswapped?\nAnswer with exactly one phrase: 'authentic' or 'faceswapped'.\nAnswer: {answer}\n\n" },
        { "type": "image", "image_id": "target_image" },
        { "type": "text", "text": "Is the face in this image authentic or faceswapped?\nAnswer with exactly one phrase: 'authentic' or 'faceswapped'.\nAnswer:" }
      ]
    }
  ],
  "response_format": {
    "type": "single_phrase",
    "real_word": "authentic",
    "fake_word": "faceswapped",
    "match": "first"
  }
}
\end{lstlisting}

\paragraph{Dynamic Assembly and Label Resolution.}
At runtime, the execution worker dynamically expands and populates the prompt based on the study configuration:
\begin{enumerate}
    \item The pair of \texttt{demo\_image} and \texttt{demo\_text} blocks is repeated $n$ times according to the requested demonstration count ($n \in \{1, 2, 4, 6, 10\}$) and composition order.
    \item For each repetition, the worker injects the file path of the demonstration frame into \texttt{demo\_image}.
    \item In \texttt{demo\_text}, the \texttt{\{answer\}} placeholder is automatically replaced with the ground truth label word defined in \texttt{response\_format}: resolving to $w_{\text{real}}$ if the demonstration image is real, and $w_{\text{fake}}$ if it is fake.
    \item Finally, the test frame is injected into \texttt{target\_image}, followed by the classification question ending with the \texttt{Answer:} prompt cue where the model begins generating its output.
\end{enumerate}

\paragraph{Demonstration Provenance and Metadata Logging.}
To allow rigorous downstream analysis of few shot dynamics, every evaluated record emitted by the pipeline preserves the exact sequence of demonstration images in the order they were presented to the model. Each output entry logs a structured \texttt{demo\_config} containing the list of demonstration file paths alongside their assigned labels:
\begin{quote}
    \texttt{\scriptsize [\{"path": ".../frame29.jpg", "label": "real"\}, \{"path": ".../frame29.jpg", "label": "fake"\}, \dots]}
\end{quote}
Recording this full demonstration lineage directly within each prediction record enables detailed post hoc evaluations, such as examining how specific demonstration orderings, generator types, or individual exemplar choices influence model predictions.

\paragraph{Engine Configuration Overrides.}
By default, inference engines such as vLLM limit multimodal input to a single image per request. Because an $n = 10$ few shot prompt carries $10 + 1 = 11$ images simultaneously, the study configuration passes an engine override in the model configuration:
\begin{equation}
    \texttt{limit\_mm\_per\_prompt} = \{\texttt{image}: 11\}
\end{equation}
allowing the model to process all demonstration images alongside the target query frame within the same context.

\subsection{Evaluation Protocol and Configuration Selection}
\label{subsec:fewshot_selection}

\paragraph{Exploration Matrix on the Development Set.}
Following the same methodology as in the zero shot stages (\Cref{subsec:devset,sec:staged_prompting}), we first evaluate candidate configurations on the balanced development sets of FOWS and GOTCHA (\num{1344} frames each) to identify the optimal few shot setup for each model, before running evaluations on the full benchmark test partitions.

For each of the top three models (\texttt{Qwen3.6-35B-A3B}, \texttt{google/gemma-4-31B-it}, and \texttt{Qwen3.6-27B}), the pipeline evaluates every combination of the experimental axes:
\begin{equation}
    2 \text{ datasets} \times 4 \text{ pools} \times 4 \text{ compositions} \times 5 \text{ counts } (n) = 160 \text{ units per model}
\end{equation}
Across the three models, this yields 480 evaluation units and \num{645120} total inference queries on the development sets.

\paragraph{Pool Averaged Selection Protocol.}
For each candidate pair of demonstration count and composition $(n, \text{composition})$, the model is evaluated on both development sets under each of the four demonstration pools $\mathcal{P} = \{\texttt{fows\_occ}, \texttt{fows\_noocc}, \texttt{gotcha\_occ}, \texttt{gotcha\_noocc}\}$. The score across the two development sets is computed using the overall MCC definition from \Cref{eq:mcc_overall}:
\begin{equation}
    \text{MCC}_{\text{overall}}(p) = \frac{\text{MCC}_{\text{FOWS}}(p) + \text{MCC}_{\text{GOTCHA}}(p)}{2}
\end{equation}
To select the configuration that performs best across all visual conditions rather than overfitting to one specific pool, we compute the average of $\text{MCC}_{\text{overall}}$ across all four pools:
\begin{equation}
    \overline{\text{MCC}}_{\text{overall}} = \frac{1}{4} \sum_{p \in \mathcal{P}} \text{MCC}_{\text{overall}}(p)
\end{equation}
For each model, the pair $(n, \text{composition})$ that achieves the highest $\overline{\text{MCC}}_{\text{overall}}$ on the development sets is selected as its optimal few shot configuration.
